---
title: 'Target connections and task routing'
description: 'Share MCPHub across applications while keeping credentials and task state separate.'
---

An MCP registration can expose multiple **exact targets**, such as `project/official` and
`project/synthetic`. Target paths are operator-defined labels; MCPHub does not interpret
benchmark names, create task containers, or require a Docker socket.

## Persistent targets

In the server editor, open **Target connections** and add a target with its own HTTP/SSE
URL or stdio command and credentials. Use one logical MCP name for all targets. Each
static target owns an independent upstream client; credentials and transport settings do
not fall back to the parent registration or another target. Only toolchain environment
settings are inherited by target child processes; provider credentials must be explicitly
configured in the target. An explicit environment value such as `${NOTION_API_KEY}`
may resolve a configured Hub environment variable.

Supply `X-MCPHub-Target: project/official` on **every** MCP request, including
initialization and tool discovery. Missing, unknown and unauthorized targets are rejected.
Targets can allow specific Bearer Key **IDs** or usernames; empty access lists permit
administrators only. Parent-server visibility and ordinary Bearer Key scope still apply.
An explicit access list also applies to administrators. Target routing does not rename tools. Target connections use their explicitly configured
credentials; automatic upstream OAuth enrollment is disabled for targets to prevent
sharing one logical server's OAuth state across workspaces. Configure a target-specific
Authorization header when the upstream requires an access token.

Multiple keys in a pool must refer to the **same** provider account resources. Separate
Notion workspaces, Slack workspaces or databases belong to different targets, not a rotating
key pool. This version's automatic key rotation supports Context7 and TwelveData;
other providers use their normal MCP credentials. Keys are shown by their masked suffix.

Rate settings belong to the logical MCP registration and are shared across its targets,
tasks and callers. Compatible stdio wrappers can also consume the managed relay environment.
Turning on relay does not make an arbitrary MCP wrapper proxy-aware automatically.
Configure the IP pool connection and credentials once on **Relay settings**. Compatible
connections expose only **Route through the IP pool**; native, unadapted MCPs show a
non-interactive explanation. Relay URL/token fields are hidden from the connection's
ordinary environment editor.

New wrappers read `MCP_RELAY_URL`, `MCP_RELAY_TOKEN` and
`MCP_RELAY_TIMEOUT_SECONDS` and declare `MCPHUB_RELAY_ADAPTER=fetch-v1` in their
connection environment. The declaration describes a real `/v1/fetch` implementation;
it does not implement one. Hub recognizes older delivered wrapper paths as well.
Only the canonical names above are read and injected.
A disabled switch clears relay URL and token values at runtime.
Task connection configurations can retain the same adapter declaration without
embedding credentials. The callback adapter must apply the relay snapshot to its runtime.

## Native implementations, wrappers and versions

Different targets of one logical MCP can run different implementations simultaneously.
Each target has an independent **enabled** switch, optional **implementation** label
(`native`, `wrapper`, `custom`) and **version** label (up to 160 characters).
An omitted enabled flag means enabled. Disabled targets reject both new and existing
callers, including task registrations; they never fall back to another implementation.
Other targets keep their own configuration and clients. Editing a target retires its
changed client; editing shared connection controls can retire clients of all targets.
In-flight calls can finish on the previous configuration.

The labels do **not** install or select a package version. Pin the executable/package
in the target's command and arguments, or pin the external runtime image by tag/digest.
For example, two stdio targets can execute `/opt/mcp/native/v1/server.mjs` and
`/opt/mcp/wrappers/suite-a/server.mjs` with separate credentials. A third target can use
`http://mcp-native:8080/mcp`. Tools are discovered from the selected implementation;
MCPHub does not translate incompatible schemas between versions.

The editor can **create a target from the current connection** for supported ordinary
stdio/HTTP connections, or **copy a target**. Copies start disabled. Set the exact path
and verify credentials and the launch command before enabling a copy. Creating the
first target switches that registration to explicit target routing; the parent connection
is no longer a default. Connections with automatic OAuth, personal credential templates,
session isolation or proxy configuration must be configured explicitly rather than copied.

Compatible lightweight MCPs can share Hub's installed runtime, using separate processes
and pinned paths. Conflicting dependencies or different OS/runtime requirements belong in
separate containers. The optional Compose example at
`examples/multi-implementation/compose.yaml` attaches external HTTP runtimes to the
`mcphub-runtime` network created by this repository's deployment Compose file. Supply
`MCP_NATIVE_IMAGE` and `MCP_WRAPPER_IMAGE` with operator-built, pinned HTTP MCP images,
plus globally unique `MCP_NATIVE_NAME` and `MCP_WRAPPER_NAME` container names, then
run `docker compose -f examples/multi-implementation/compose.yaml up -d`.
Connect to `http://{MCP_NATIVE_NAME}:8080/mcp` and `http://{MCP_WRAPPER_NAME}:8080/mcp`.
Use the unique container names rather than generic service aliases when multiple
Compose projects share this network, so their destinations cannot collide.
No extra host port is required. Images must actually implement HTTP MCP at those paths;
the Compose example does not turn an arbitrary stdio image into an HTTP server.
Hub neither manages Docker containers nor receives the Docker socket.

Saving Hub-owned credentials reconnects the relevant registration for subsequent calls.
Existing in-flight calls retain their connection. Hub cannot rewrite environment variables
inside an independently started container; recreate that runtime when its startup secrets
change. Task runtimes retain their startup snapshot until the adapter creates a new task.

### Runtime inventory

Server management displays each registration's active connection count. Expand a server
to see configured targets and the live connection inventory: implementation, configured
version, MCP-reported version, resolved package version where available, connection state,
task ID and lease expiry. `GET /api/servers` returns this metadata as `runtime` for
administrators and server owners. Shared users do not receive the inventory or other
applications' task IDs. No transport URL, command, credentials or capability token is
included in the inventory. `targetManaged` is a safe boolean available to all visible callers.

Counts represent connected upstream clients and unexpired task registrations, **not Docker
containers**. A registered task callback is not a successful health check. Connecting clients
are counted separately; configured but unused targets count as zero. Static targets connect
on first use and release their cached client after five idle minutes. Replaced clients still
serving calls appear separately as draining. Version labels remain distinct from runtime
versions; unavailable versions are shown as unknown. The inventory refreshes with the server
list (normally every 30 seconds, or immediately using Refresh).

## Task connections (tool-http-v1)

A task adapter starts its own isolated runtime and publishes two authenticated HTTP callbacks:

- `POST {callback}/list-tools` → a JSON array of MCP tools with names prefixed `server_`.
- `POST {callback}/call-tool` with `{ "tool_name": "server_tool", "tool_args": {} }`
  → `{ "content": [...], "isError": false }` (or `isError: true` for tool errors).

Configure a target with `kind: "task"`. An operator with a system all-access Bearer Key
or dashboard administrator identity registers the callback:

```http
POST /api/task-connections
Authorization: Bearer OPERATOR_KEY
Content-Type: application/json

{"server":"filesystem","target":"project/official","taskId":"unique-task-id","url":"http://adapter/internal/opaque-task-route","token":"CALLBACK_SECRET"}
```

The response `data` contains `id`, `token`, `expiresAt` and `path`. The returned task
capability is usable only for this connection, at `POST {path}/list-tools` and
`POST {path}/call-tool`, with `Authorization: Bearer {token}`. URLs must be fixed by the
trusted adapter, not supplied by models. MCPHub forwards with the separate callback secret,
rejects redirects, limits response size, and applies the registered MCP's scheduler and audit.

Connections expire after **300 seconds**. Renew with `PUT /api/task-connections/{id}`
using the registering operator's identity; delete with `DELETE` before destroying the
runtime. Missing, expired, revoked and cross-task capabilities cannot route requests.
Restarting MCPHub clears all leases; adapters must fail closed and create new task sessions.
The tool-http-v1 gateway is a separate adapter protocol on the **same Hub HTTP port**;
it does not impersonate a public MCP server transport.

An authorized adapter can fetch `GET /api/servers/{name}/runtime?target=project/official`
for a relay-only `data.env` snapshot before creating a task runtime. Provider keys are
not included. The adapter determines how its wrapper consumes these environment variables.

## Statistics and logs

The dashboard has separate **Call logs**, **Statistics** and **Runtime logs** tabs.
Call logs default to tool calls and errors; HTTP attempt sources can be selected separately.
Statistics stream complete durable audit files for the selected month or UTC date range
(maximum 366 days). Each completed tool call counts once, regardless of internal key attempts.
An invocation still in progress is not yet counted. No quota usage or provider request count
is inferred from tool counts.

The statistics API returns one row per MCP, aggregating calls across its targets and
clients: `GET /api/logs/statistics?start=...&end=...&server=...`. Select a month or a UTC
date range in the dashboard; the server filter is optional. Model, benchmark and run
labels are not collected or used. Existing audit files remain usable for these totals.
Target paths and task IDs still identify connections in logs and runtime inventory.
Enable `MCPHUB_AUDIT_LOG_DIR` to persist the tool records used for these statistics.
Arguments, results and full keys are not written to audit logs.

Target names may be a single identifier (`atlas`) or an exact slash-separated name
(`atlas/official`, `other/suite/workspace`). Slashes are optional and never imply
inheritance. Creating another workspace copies the existing MCP launch settings;
provider credentials are edited as individual environment-variable rows.
Hub client access IDs are separate from provider credentials and live in advanced settings.
