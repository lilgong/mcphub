---
title: 'MCP-Atlas integration'
description: 'Host Atlas shared MCP servers using existing Hub credentials, authentication and activity logs.'
---

MCPHub hosts selected shared MCP processes. Atlas keeps its HTTP compatibility
entrypoint, tool names and disposable task containers. Direct mode retains its existing rate gates. No Yibu HTTP
proxy or separate key/token management is required.

## Independent deployment and package import

Build Hub from its own Dockerfile. It never mounts an Atlas checkout or inherits
an Atlas runtime image:

```bash
cd ~/mcphub
docker build -t mcphub:standalone .
docker compose --env-file data/database.env -f compose.local.yaml up -d
```

Build modified shared MCPs separately separately from Hub. The delivered `mcp-buddle` folder contains only importable `.mcpb` files and an installation guide. Each versioned `.mcpb` contains its pinned
MCP, wrappers and Node dependencies or Python runtime, without real keys,
task data or the Atlas HTTP application. Current artifacts target Linux x86_64
and the project's Debian Docker image; rebuild for other platforms.

On **Servers**, choose **Upload**, select a package, and set its logical MCP name
(e.g. `brave-search`). Fill credentials and enable it. Persist `/app/data`, which
contains the installed packages. Native MCPs can still use the marketplace or
the upstream launch command. Package names include the source revision, so
importing a different version does not replace an older package.

For one version, use the normal connection form. For multiple versions or
workspaces, expand **Multiple versions or workspaces (optional)**, convert the
existing connection into the first target (preserving credentials), assign a
path such as `atlas/official`, and add further connections. Only target settings
are used after conversion. Clients must supply the exact target; no fallback
occurs. A version label does not install that version.

**Key rotation** appears only for recognized stdio Context7 / TwelveData
adapters. When enabled, it hides the overridden single-key field; disabling it
restores the saved value. Supporting another MCP requires an adapter for its
credential injection and quota errors. Distinct Notion / Slack workspaces
belong in separate targets, never an interchangeable key pool.

Tool rate limits have their own section and are shared across all targets and
clients. Queue and concurrency settings are advanced options. Relay has a
separate connection section and requires a relay-compatible wrapper.
For Yibu, configure `BRAVE_API_KEY`, `EXA_API_KEY`, `LARA_YIBU_API_KEY`,
`WEATHER_YIBU_API_KEY`, or `OXYLABS_USERNAME` / `OXYLABS_PASSWORD`.
Saving credentials recreates the affected connection and may interrupt active
calls. Ordinary configuration values use normal settings storage; use personal
Credentials bindings when encrypted per-user storage is required.

Eye buttons toggle credential visibility locally without changing or submitting values.
Keep imported STDIO commands and arguments. `/app/data/mcp-usage` and package
`PYTHONPATH` entries are absolute paths inside the Hub container. The Yibu WeatherAPI
package requests Yibu directly and does not require managed Relay.

## Connect Atlas

Create a key on the existing **Bearer Keys** page. Give it access to the selected
servers (and an owner if using personal credentials). Configure Atlas's root `.env`:

```dotenv
MCP_TOOL_TRANSPORT=hub
MCPHUB_URL=http://host.docker.internal:3002
MCPHUB_TOKEN=<existing Hub Bearer Key>
MCPHUB_SERVERS=brave-search,exa,lara-translate,weather-data,oxylabs
MCPHUB_NAME_SEPARATOR=-
MCP_SHARED_AGENT_IMAGE=mcp-atlas-runtime:mcphub
MCP_TASK_AGENT_IMAGE=mcp-atlas-runtime:mcphub
```

Use the same separator as Hub's routing setting and keep imported server names
unchanged. Atlas connects separately to `/mcp/<server>` using Streamable HTTP;
it removes Hub's server prefix before its router adds Atlas's original prefix.
Only selected servers are replaced, so Atlas never starts duplicate local MCP
processes for them. In auto-enable mode these servers do not require upstream keys
on Atlas. An explicit `ENABLED_SERVERS` allowlist still applies.

Restart the shared Atlas runtime to load transport changes. Returning to
`MCP_TOOL_TRANSPORT=direct` uses the original Atlas configuration and keys.
Existing task isolation and shared-account write policy remain in Atlas. Main is
unchanged, and the integration branch supports both modes. Only selected Hub
services delegate their rate gates; other services retain the original behavior.

## Logs and counts

Use **database mode** (`USE_DB=true` and `DB_URL` pointing to PostgreSQL with the
extensions supported by Hub) to enable the existing **Activity** page. It records
MCP tool-call counts, outcome and duration. Configure
`systemConfig.activityLog.storeToolPayload=false` for metadata-only activity logs.
Activity records count MCP calls, not upstream HTTP attempts.

The modified Yibu MCPs also append durable `started` and `finished` events for
**each actual upstream request** to `/app/data/mcp-usage`. Bind-mount `/app/data`
to preserve these logs. A failure to write/fsync the start event prevents the
request; each retry creates another request ID. A start without a finish means
an interrupted or incomplete request, not necessarily a failed upstream request.
Count `started` events to count attempts; never count both event types as calls.
Only hashed credential identifiers and safe metadata are logged, without keys,
queries or bodies. Events are emitted on stderr into Hub's existing **Logs** page
as well; that page keeps a limited in-memory history, while files are durable.
Tool activities and upstream requests are distinct records; they are not yet
joined by a task or tool-call ID. Logs are not automatically expired.

The dashboard, MCP endpoint and logs use the same Hub port. No extra HTTP port,
proxy credentials or Yibu-specific settings store is introduced.

The Atlas Hub image also enables `MCPHUB_AUDIT_LOG_DIR=/app/data/tool-audit`. Every
MCP tool invocation is durably audited before execution; failure to write prevents
execution, independently of Activity database availability. Tool arguments, results
and keys are omitted. These events also appear on the existing Logs page.

`compose.local.yaml` provides Hub on port 3002 and internal-only PostgreSQL to
enable the existing Activity page. Supply private `data/docker.env` (admin/JWT)
and `data/database.env` (`POSTGRES_PASSWORD` and `DB_URL`), then run
`docker compose --env-file data/database.env -f compose.local.yaml up -d`.
In database mode, web edits are stored in the database; do not overwrite them by
reimporting stale settings.

## Per-service scheduling and relay

Each registered MCP editor has **Call limits and relay** settings. Tool limits
are shared by all callers of that registered server, including different users,
clients and groups. Optional fields include a rolling-window call budget,
minimum start interval, concurrency and 429 cooldown. Unset rate/concurrency
fields impose no extra limit. Waiting defaults to 60 seconds and can be changed;
client cancellation removes queued calls. Policy edits apply live without
reconnecting a server. The scheduler never automatically replays a tool call.
Scheduling is local to one Hub process and resets on restart. Separately
registered copies and clients bypassing Hub do not share this scheduler.

Reviewed export presets retain Brave's 1500 ms start spacing and TwelveData
Basic's 8000 ms spacing plus 8 calls per 60-second rolling window. This is
only a single-credit approximation: endpoint-weighted credits and the 800/day
budget are not yet enforced. Other MCPs receive no invented concurrency or
rate defaults. The Open Library wrapper paces each HTTP request at 1000 ms;
change `OPEN_LIBRARY_MIN_INTERVAL_MS` in its environment to change this rate.

`compose.local.yaml` sets `MCP_RATE_LIMIT_MAX=off`, disabling only the aggregate
MCP transport IP guard. Login, registration and dashboard API guards remain.

Durable tool audit records now include queued/dispatched/completed events,
wait and execution duration, safe error category, HTTP status where available,
and cooldown. These events share the tool request ID and appear in Logs.
Count `started` records for tool admissions and `dispatched` for executions;
never count every diagnostic event as another invocation. Arguments, response
bodies, credentials and raw error text are not included.

In Hub mode, `MCPHUB_MANAGE_RATE_LIMITS=true` (default) delegates only selected
services’ outer tool gates. Set it to `false` when connecting to a Hub without
these policies. Direct mode never delegates them.

The admin **Relay settings** page manages the existing relay URL, encrypted token and HTTP
timeout. It keeps upstream proxy credentials in the residential relay daemon. The
HTTP limits section uses authenticated `/v1/limits` on the existing relay port:
limits apply live and persist in `limits.json` next to its audit log. Older
relay versions must be upgraded before using these controls. ArXiv keeps 3-second
spacing and one active request; Nominatim/routing keep 1-second spacing. NCBI
E-utilities separates anonymous (334 ms) and keyed (100 ms) requests; PMC uses
a separate conservative policy. Wikipedia uses a project-identifying User-Agent,
300 ms spacing and one active request. Overpass has no invented fixed interval
and observes upstream 429 cooldown. These are application controls, not additional
provider quota or a way to bypass other clients sharing a key. OSM and Wikipedia reload when connection settings change.
Their compatibility wrappers retain HTTP pacing. To fetch an authorized relay-only
snapshot when creating new isolated Arxiv/PubMed task containers, opt in:

```dotenv
MCPHUB_MANAGE_RELAY=true
MCPHUB_CONFIG_URL=http://127.0.0.1:3002
```

`MCPHUB_CONFIG_URL` is reachable from the completion host; `MCPHUB_URL` is reachable
from Atlas containers. The existing operator Bearer Key must allow each requested
Arxiv/PubMed server (or all). Ordinary user keys cannot read the shared token.
Snapshots contain only relay settings; no Hub token is passed to task containers.
If opted in, a failed configuration fetch prevents task startup rather than using
stale credentials. Already running tasks keep their snapshot. Direct mode uses
its existing environment and never reads this endpoint. Save-and-disable clears
managed relay variables for new tasks and reloaded Hub services.


Relay HTTP attempts have durable `http_started` / `http_finished` records,
including retries, status and safe network error type. A start write failure
prevents the upstream request. Summaries include queue delay, attempt count,
Retry-After and client disconnects. Tool and relay HTTP IDs are not yet joined.


The admin **Logs → Call logs** view defaults to errors only. Filter by HTTP
status (including 429, 4xx, 5xx and common individual codes), source, MCP/host
and UTC date; timestamps display in the browser's local timezone. Tool successes
do not imply upstream HTTP 200. Timeouts, cancellation and queue failures can
be found under **No HTTP status**. Each finished tool invocation appears once;
Yibu and Relay rows represent individual HTTP attempts and should not be added
to tool rows as a single invocation count. Runtime logs remain in a separate tab.

The reader exposes selected metadata only and reads bounded recent file tails;
a warning indicates when older records are outside the displayed window. Complete
JSONL files remain on disk. Relay visibility uses `MCPHUB_RELAY_LOG_FILE`, mounted
read-only from the local relay log directory in `compose.local.yaml`; remote
relay daemons need their log files made available separately. This does not add a
new port. Call logs require admin access and are not removed by clearing runtime
logs.

## Context7 and TwelveData key rotation

Edit the original registered stdio MCP and open **Multi-key rotation**. Select
Context7 or TwelveData, add keys, enable rotation, and save. Leave rotation
disabled to keep the original single-key path. This implementation targets the
Atlas-packaged Context7 (Node fetch) and TwelveData (Python httpx) MCPs; it does
not change their tools or require importing separate MCPs for each key. The
pool configuration uses the same protected server configuration storage and
owner/admin read permissions as existing environment credentials.

HTTP requests rotate through available keys across all callers. Explicit
quota/authentication failures and 429 responses try the next key inside Hub;
ordinary input/document/permission errors, 5xx and network failures do not
rotate. A request tries each key at most once and shares a 55-second HTTP
budget. Failed keys remain configured. Retry-After/RateLimit-Reset take precedence;
explicit daily/monthly quota errors otherwise cool down until the next UTC
day/month. Other key failures cool down for 60 seconds and then participate
again. Changed key values take effect on the next request. Runtime cursors and
cooldowns are process-local and reset on Hub restart. Existing shared MCP limits
remain in force; key rotation does not automatically change them.

All keys with quota/authentication failures return a safe error prefixed with
`Error: KEY_POOL_EXHAUSTED`, compatible with Atlas's existing account guard.
If any key is only temporarily rate-limited, the final error is a recoverable
HTTP 429 instead. Intermediate failures are hidden from the model but remain
visible in **Logs → Call logs → Key pool HTTP**, including the last six key characters, HTTP status,
error category and recovery time. HTTP 200 can still be an error if TwelveData
returns an error code inside JSON. No key values, query strings, response bodies
or raw exception text are written to these audit files. Every actual upstream
attempt requires a durable start record before using its key.

The adapters call a capability-protected `/internal/v1/key-pool/:name` endpoint
on the existing Hub port. Each child receives a random per-server process-local
capability; it can only access the configured provider's fixed HTTPS host and
read-only API paths. Pool values stay in Hub, and children receive a placeholder
single key. This feature applies to Hub mode; Atlas direct mode is unchanged.

The Hub-only TwelveData preload also omits the pinned package's two non-object
optional output schemas, which the current Hub SDK rejects. Tool names,
input schemas and results remain unchanged; valid object output schemas remain.


**Activity & logs** is the single dashboard entry for diagnostics. Call logs
open with error/status filtering; **Statistics & details** preserves the former
Activity page's tool-call statistics and detailed records when database mode is
available. **Runtime logs** remains the process diagnostic stream. The legacy
`/activity` URL redirects to `/logs?view=activity`. These views are not combined
into an additive invocation count because tool records and HTTP attempts have
different meanings. Runtime streaming is subscribed only while that view is open.

Key pool entries no longer require names: the editor and new HTTP audit records
automatically show a masked suffix, normally the last six characters. Short keys
always retain at least one hidden character. Existing key IDs and values are
preserved, and legacy labels are ignored for new attempts.

## Call statistics

Select a month or custom UTC date range to count completed calls, successes and errors per MCP. No model, benchmark or run labels are configured or collected. Target paths still select implementations/workspaces, and task IDs still identify isolated task connections. Existing audit records remain available for time-range totals.

## One Relay configuration entry

Configure the shared IP pool URL, token and HTTP limits on **Relay settings**.
Supported MCP connections expose a single enable switch; unsupported connections
cannot enable it. Arxiv, PubMed, OSM and Wikipedia delivery packages use the generic
`MCP_RELAY_*` convention and declare their `fetch-v1` adapter. Already imported packages
keep working through the legacy aliases injected by Hub, without reimporting.
