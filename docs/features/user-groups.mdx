---
title: 'User groups and calling Keys'
description: 'Grant one application access to selected MCP servers and exact targets.'
---

Administrators manage accounts and access groups in **Users & groups**. The folder
list selects a group; the user table manages its members. **MCP routes** is the
separate connection aggregation feature; it does not grant group access.

1. Create or rename a group in the folder list.
2. Drag a user onto a group, or use the group selector in the user table. Moving
   removes previous memberships and assigns the destination in one atomic update.
   Dragging to **Ungrouped** explicitly removes all memberships. Existing multiple
   memberships are retained until the administrator moves that user.
3. Open **Group permissions** and select MCP servers. Each multi-target server
   lists its targets directly: choose one or several without a separate mode switch.
   **Select all** chooses the currently registered servers and targets; newly added
   targets require a separate grant. Legacy API grants with omitted `targets` still
   mean all targets, including future ones.
4. Generate the group's calling Key and save the complete token shown once. A Key
   calls all resources allowed by its group. Manage its enabled state or deletion
   in Settings. Deleting the old Key allows generating a replacement in the group.

Membership management requires an administrator. `PUT /api/user-groups/membership`
accepts `{ "username": "alice", "groupId": "destination-group-id" }`; use `null`
for `groupId` to move to Ungrouped. The update is serialized with group edits so
concurrent moves do not lose another user's membership or briefly remove all
restrictions during a move. Enabled memberships still combine by union for clients
that maintain multiple memberships through the API.

A group Key uses only its own group's permissions, regardless of user memberships.
An unbound system Key with all-access scope remains a shared/operator Key; Users & groups
also offers an explicit button to create one. Existing scoped Keys keep their restrictions.

For target-managed servers, include the exact target on every MCP request:

```http
POST /mcp/slack
Authorization: Bearer MCPHUB_GROUP_KEY
X-MCPHub-Target: atlas/official
Content-Type: application/json
```

Target selection is independent of the calling Key. The editor uses
`application/category`: `atlas/official`, `atlas/syn-1`, `other-benchmark/default`.
The Hub does not interpret these labels or route to another target when a target is
missing, unknown, disabled, or forbidden. Ordinary single connections do not require this
header. Provider API Keys belong to the MCP connection; group Keys authenticate Hub clients.

Permissions are checked against live configuration, including established sessions.
Removing access or disabling a group blocks subsequent requests. Deleting a group leaves
its Key bound to the deleted group and denied; it never becomes a shared Key. Disabled
membership groups also deny access until enabled or the membership is explicitly removed.
Administrator identities retain management access. Legacy explicit target access lists
remain additional restrictions.

Group Keys cannot access general dashboard management APIs. They can register task
callbacks for allowed resources, renew/remove their own leases, and read the scoped relay
runtime snapshot. See [Target connections](/features/target-connections).
