---
title: 'Users and owned calling groups'
description: 'Let each user organize authorized MCP servers and targets behind scoped calling keys.'
---

Users own resources. Calling groups belong to users and narrow the resources their clients
may invoke. A user can create several groups and include the same authorized server in
more than one group. Groups do not contain user members.

## Dashboard

Ordinary users see **Groups** and manage their own groups. They can select their own MCP
servers, public servers, and servers explicitly shared with them. Other users' private
servers and restricted targets are not selectable. The dashboard's server visibility and
configuration management rules continue to apply independently of calling groups.

Administrators see **Users & groups**, with users as collapsible headings and their owned
groups beneath them. They can create users, create a group for a selected user, edit a
group's resources, and manage its calling key. Selecting resources for another user applies
that user's access rules, even when the administrator edits the group. Group ownership is
fixed after creation; edit the name and grants without moving the group between owners.

Open **Group permissions** to select registered servers and exact targets. **Select all**
selects the resources available to the group owner. New target grants use explicit paths.
Open **Calling key** to create, enable, disable, delete, or replace the group's key. Save
the complete token displayed once; subsequent reads return a masked value. No separate
personal key or username parameter is needed for this flow.

Administrators retain an advanced link to MCP aggregation routes. Those routes aggregate
MCP tools; they are distinct from calling permissions. Unbound operator/system keys retain
their existing semantics, including the administrator's shared-key option.

## Requests and live permissions

```http
POST /mcp/slack
Authorization: Bearer MCPHUB_GROUP_KEY
X-MCPHub-Target: atlas/official
Content-Type: application/json
```

The key identifies one group and its owner. Requests inherit the owner's current resource
visibility plus the group's explicit grants. Knowing a key never permits access to another
user's private server. Revoking sharing, disabling/deleting a group or key, deleting its
owner, or changing the owner's privileges takes effect on subsequent requests, including
established MCP sessions. Target selection remains separate from the key. Single-connection
servers do not need a target header; HTTP forwarding uses the same owner and group checks.

Group keys do not grant dashboard management access. Existing administrator-owned task
registration and runtime snapshot capabilities remain supported; the existing administrator
requirement for task callback registration is retained.

## APIs and storage

- `GET /api/user-groups`: all groups for administrators, owned groups for ordinary users.
- `POST /api/user-groups`: create a group with `name`, `enabled`, and `servers`. Administrators
  may specify `owner`; ordinary users can only create groups for themselves.
- `PUT /api/user-groups/{id}` and `DELETE /api/user-groups/{id}`: owner or administrator only.
- `GET /api/user-groups/resources?owner={username}`: safe selector metadata, without
  transport configuration, credentials or task runtime identities. Only administrators can
  request another owner's selector.
- Existing `/api/auth/keys` APIs manage group-bound keys under owner/admin authorization.

Ownership is stored inside the existing system configuration JSON in both file and database
modes. At startup, legacy groups are assigned to the administrator (`admin` when present,
otherwise an existing administrator). The migration removes old user membership fields and
binds legacy group keys to that owner while preserving group IDs, tokens, enable flags, key
kinds, and grants. It is idempotent and does not regenerate keys. Deleted groups leave their
keys bound and denied; they never turn into unrestricted shared keys.

Develop and test the upgrade in isolation. Deploy its backend and dashboard together after
active benchmarks finish; the existing service does not load source changes automatically.
