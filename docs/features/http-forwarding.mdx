---
title: HTTP Forwarding
description: Manage ordinary HTTP APIs alongside MCP servers without changing their client protocol.
---

HTTP forwarding is a separate server type (`http-proxy`). Unlike Streamable HTTP, it does not perform an MCP handshake. Unlike OpenAPI import, it does not convert endpoints into MCP tools. Register the resource in **Servers**, configure its upstream base URL and headers, then use the generated client base URL. Displayed and copied URLs use **Settings → Base URL**, independently of the browser or reverse-proxy address. Set it for each deployment; no source changes are needed.

## Configure Serper

Import `examples/http-forwarding/serper.json` through JSON import, or create a server named `serper` with type **HTTP forwarding**:

- Upstream base URL: `https://yibuapi.com/serper`. The path prefix restricts this resource to Serper.
- Authentication: **Bearer**. Enter only your upstream API key; the dashboard adds the Authorization header and Bearer prefix automatically.
- Client base URL: `http://YOUR_HUB:3002/http/serper`.
- Search endpoint: `http://YOUR_HUB:3002/http/serper/search`.

Authenticate client requests with a Hub shared, user, or user-group bearer key. Grant the group access to `serper` in **Users and groups**. Client keys and cookies are not copied upstream. Shared keys retain their existing scope; user keys also retain server visibility restrictions. Permissions are checked before queuing and again before dispatch.

For official Serper, set the upstream base URL to `https://google.serper.dev`, select **API key header** with header name `X-API-KEY`, enter only the key, and call `/http/serper/search`. An upstream URL can also use a Hub environment placeholder such as `${SERPER_UPSTREAM_URL}`. Recognized Yibu and official Serper URLs preselect the corresponding authentication mode until the user chooses one explicitly. Other HTTP APIs can use Bearer, a custom API-key header, or no authentication; extra headers remain under a collapsed advanced section. Existing stored headers are recognized when editing and require no migration. Values entered directly in the dashboard apply to subsequent requests without restarting the Hub.

## Benchmark clients

Keep existing search parameter generation, response parsing, and retry behavior. Change only the upstream URL/base URL and credential:

- claw-eval: set `SERP_API_URL` to the Hub search endpoint, and set its search key to a Hub key.
- Toolathlon: set `serper_api_base_url` to `http://YOUR_HUB:3002/http`, and `serper_api_key` to a Hub key. Its existing `/serper/search` suffix selects the `serper` resource and `/search` endpoint. Keep the resource name `serper` for this configuration.

The forwarding layer preserves the request body, query string, upstream response body, status code, Content-Type, Retry-After, ETag, Last-Modified and supported rate-limit headers. It makes one upstream attempt per accepted request and does not automatically retry or follow redirects.

## Limits, audit and deployment

Existing per-resource call limits apply to HTTP requests across all clients of one Hub process. No default rate or concurrency cap is added. Limits are not coordinated across multiple Hub replicas.

Configure `MCPHUB_AUDIT_LOG_DIR` to a persistent, writable directory. Every dispatched request is audited before any upstream credential is used; without durable auditing, HTTP forwarding fails closed. HTTP statuses and durations appear in **Call logs**, including status filtering, and calls appear in time-range statistics. Queries, request bodies, response bodies and full keys are not written to the audit. Credential fingerprints and four-character suffixes identify configured keys.

HTTP forwarding is implemented in the project code and included in builds/images of this branch. Resource settings use the existing JSON or database server storage, including import/export; no extra process or port is needed. Mount the settings and audit directory outside the container before deployment. Existing deployments do not change until a new build is deployed.

HTTP request and response bodies stream with backpressure, preserving binary and compressed bytes without fixed 1 MiB/8 MiB payload limits. The configured request timeout still applies; client disconnection cancels the upstream request. Business headers, including conditional requests and checksums, are retained. Hub credentials, client credential headers, cookies and hop-by-hop headers are isolated; configured upstream credentials take precedence. Redirects remain under client control: `Location` is preserved and same-resource locations are rewritten to continue through Hub. MCP target connections, MCP key-pool adapters, wrapper Relay routing, browser cookie sessions and WebSocket connections are not supported by this server type. Admin-owned resources may address internal upstream services; other owners are subject to the existing SSRF protections.

### Per-key usage

Register separate resources such as `serper-a` and `serper-b` to assign different upstream
keys to different callers. No multi-key rotation is introduced. Each actual HTTP attempt
writes `upstream_started` and `upstream_finished` in the persistent tool-audit directory,
with a separate upstream request ID, HTTP status, duration and credential roles. Bearer
prefixes are removed before fingerprinting. Full keys, request URLs/queries and payloads
are not logged. Very short credentials never expose their entire value through a suffix.

Call statistics now offers **Tool calls** (the existing count) and **Upstream API requests**.
The latter aggregates completed HTTP forwarding attempts, instrumented MCP usage records,
and key-pool attempts. Retries count as separate API attempts; tool audit events never
count as extra upstream calls. A request carrying multiple credential roles counts once,
even when the same key appears in several roles. Billing may use a different unit.

Administrators may enter an upstream key in statistics. The browser hashes it locally,
clears the input, and sends only the 16-hex-character SHA-256 fingerprint as `credentialId`.
The existing statistics route accepts `metric=upstream`; raw keys are not accepted there.
Browser hashing also works on private-network HTTP deployments without Web Crypto.

Coverage is partial: MCPs without upstream request instrumentation cannot supply per-key
usage, older key-pool records without fingerprints cannot be matched, and older forwarding
records lack completed credential-attributed attempts. Missing records do not prove zero
usage. This feature does not infer credentials from arbitrary environment variables.


### Encoded resource names

Both HTTP entry points retain original path and query encoding. Spaces, Unicode,
encoded slashes, percent signs, question marks and hash characters remain resource
name data. Validation rejects raw query/fragment separators, control characters,
backslashes and actual dot path segments, rather than recursively decoding object
names into a different path. The configured upstream origin and path prefix remain
fixed. Workspaces use the same validation and business-header handling; streaming
bindings retain their existing client-controlled deadlines.

### Workspace HTTP request budgets

Authenticated workspace requests can send `X-MCPHub-Upstream-Timeout-Ms` as a
positive integer in milliseconds. The header is consumed by Hub and never sent to
the upstream. HTTP read inactivity is bounded after admission; shared rate/queue
policies are unchanged. An operator's finite server timeout remains an upper bound.
Without a caller budget, a finite server setting applies; otherwise
`MCPHUB_WORKSPACE_HTTP_TIMEOUT_MS` defaults to 300000 ms. Streamed bodies reset the
idle timer on progress and do not expire solely because a large transfer takes
longer than the idle budget. gRPC unary requests use a finite execution deadline.
The client transport must reserve its own queue/delivery allowance. Timeouts do not
trigger a new HTTP replay.

Account HTTP bindings can select `egress: "ip-pool"` to use Hub's configured
`IPWO_PROXY_HOST`, `IPWO_PROXY_PORT`, `IPWO_PROXY_USERNAME` and
`IPWO_PROXY_PASSWORD`. This HTTPS CONNECT transport preserves upstream authentication,
all supported HTTP methods and streaming uploads/downloads. Pool credentials remain in
Hub; account authentication and audit records retain the selected workspace identity.
Missing pool configuration fails the request rather than silently using direct egress.
The binding's existing response/read timeout still applies. Other bindings remain direct.
